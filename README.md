# 达成编写一千万行代码的成就

本项目实现了一个用于判断奇偶数的交互式程序。不过，我们不使用取模这种奇技淫巧，而是一个数一个数地进行匹配。这样的代码手写起来很痛苦，但我们可以借助生成器，从而轻松达成编写一千万行代码的成就。

## 生成代码

想要多少行自己填。下面的示例是一千万行

```sh
node codegen.js 10000000
```

生成器会固定读取 `input.js`，然后将结果写入 `output.js`。

## 运行程序

`output.js` 就是最终要运行的程序

```sh
node output.js
```

输入一个非负整数，程序会告诉你它是不是偶数。数字存在判定范围，最小值为 `0`，最大值就是生成代码时指定的数字；超出范围会显示“超出范围”。

## 实现方式

`input.js` 中使用两个注释标记代码在哪里生成

```js
...
/* CODEGEN-BEGIN */
...
/* CODEGEN-END */
...
```

`codegen.js` 首先得到 `/* CODEGEN-BEGIN */` 前和 `/* CODEGEN-END */` 后的内容，然后往 `output.js` 中先写入标记前的内容，再写入生成的代码，最后写入标记后的内容。

为了改善性能，生成的代码不是一行一行地写入，而是一批一批地写入。通过把大量小写入合并为少量大写入，显著地减少了 IO 的次数——这对性能的影响相当可观。

### 奇偶判断程序的性能

生成一千万个判断分支后，运行 `output.js` 会发现两个明显的性能异常之处

1. 启动后需要等待很久才显示提示语。
2. 输入第一个数字后需要再次等待很久才产生回复，但第二次以及后续的回复则快得多。

由于程序存在交互过程，因此需要编写脚本 `benchmark-output.js` 来测试性能。测试脚本会启动子进程，发送标准输入，监听标准输出，并以此计时。

对于启动的性能异常

1. 启动子进程时开始计时。
2. 收到“奇偶数判断”时记录耗时。

对于回复的性能异常

1. 启动后通过标准输入发送第一个数字。
2. 每收到一次回复都要记录耗时，然后再发送下一个数字。
3. 待输入数字全部测试完后会向子进程发送 EOF。

测试 `output.js` 时依次输入 `10000000`、`9999999`、`0` 和 `9999998`；测试 `input.js` 时依次输入 `10`、`9`、`0` 和 `8`。

测试命令为

```sh
node benchmark-output.js
```

测试结果如下所示

由测试结果可知

- 启动慢是由代码量造成的。`node output.js` 的启动耗时远超 `node input.js`。不难想象，对于 `output.js`，Node.js 不仅要读取约 284 MB 的源码，还要对一千万个 `case` 进行预解析；而 `input.js` 就没这个问题。

- 第一次回复慢的主要原因是惰性解析与编译。V8 在启动时没有完整解析并编译巨大的 `isEven` 函数，直到第一次调用时才完成剩余解析并生成 Ignition 字节码。使用 `--no-lazy` 后，这部分耗时被提前到启动阶段，因此启动明显变慢，第一次回复明显变快，而二者之和则基本不变。

- 回复速度还与分支位置有关。编译完成后，靠近范围末尾的 `9999999` 和 `9999998` 仍然需要几十毫秒，而 `0` 却几乎立即返回。
